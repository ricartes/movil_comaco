# QR Transport Payload Specification

## Purpose

The origin trazabilidad QR (`movil_comaco`, `GFEQR1:` payload) carries truck plate, trailer plate and driver name as additive, pass-through fields, plus a derived matching token standing in for the driver's RUT — the RUT itself never travels in recoverable form. Neither app persists these values as new data; they exist only inside the QR ciphertext and, for name/plate, on the guias screen after decode. The QR's cryptographic keys (encryption and token derivation) are real random values provisioned from the server per empresa, never hardcoded.

## Requirements

### Requirement: Additive Payload Field Set

The producer MUST add four neutral payload keys — `patenteCamion`, `patenteCarro`, `chofer`, `rutChoferToken` — to the existing `GFEQR1:` payload without changing `v`, the envelope, or the encryption scheme. `rutChoferToken` carries the derived matching token described below, never the RUT itself.

#### Scenario: Fully populated GDE row

- GIVEN a GDE row with truck plate, trailer plate, driver name and RUT all populated
- WHEN `QrTrazabilidadService` builds the origin QR payload
- THEN the payload includes `patenteCamion`, `patenteCarro`, `chofer` with those values, and `rutChoferToken` with the RUT's derived token

#### Scenario: Partially populated GDE row

- GIVEN a GDE row missing the trailer plate
- WHEN the payload is built
- THEN `patenteCarro` is present as an empty value and payload generation does not throw

### Requirement: Producer Column Mapping Yields Non-Empty Driver Name

The producer MUST source `chofer` from its own schema's `GDE_NOM_CONDUCTOR` column, never assuming the consumer's `GDE_NOMBRE_CHOFER` naming. Given a populated `GDE_NOM_CONDUCTOR`, the resulting `chofer` value MUST be non-empty.

#### Scenario: Correct schema resolution

- GIVEN `movil_comaco`'s local GDE row has `GDE_NOM_CONDUCTOR` populated
- WHEN the payload is generated
- THEN `chofer` is a non-empty string equal to that column's value

### Requirement: RUT Never Travels In Recoverable Plaintext Form

The payload MUST NOT contain the driver's RUT in any recoverable plaintext form. Instead, when the RUT is populated, the producer MUST compute `rutChoferToken` as a keyed, truncated HMAC over the RUT, using the server-provisioned key described under key provenance below. The consumer MUST derive the identical token locally (from a candidate RUT it already holds) to test for a match; it MUST NOT attempt to recover the RUT from the token.

#### Scenario: Token present when RUT populated

- GIVEN a GDE row with a populated RUT
- WHEN the payload is built
- THEN `rutChoferToken` contains the keyed truncated HMAC of that RUT, and no field in the payload contains the raw RUT string

#### Scenario: Token absent when RUT missing

- GIVEN a GDE row with no RUT populated
- WHEN the payload is built
- THEN `rutChoferToken` is absent or empty, and payload generation does not throw

### Requirement: Backward and Forward Compatibility

Consumer validation (`validarPayloadQrTrazabilidad`) MUST continue requiring only `tipo` and `qrId`, and MUST tolerate unknown or absent keys. No payload version bump is permitted.

#### Scenario: Old QR read by new guias

- GIVEN a QR generated by the current production `movil_comaco` build (no transport keys)
- WHEN a post-change guias app decodes it
- THEN validation succeeds and the transport fields render using the missing-value pattern

#### Scenario: New QR read by old guias

- GIVEN a QR generated by a post-change `movil_comaco` build (with transport keys and `rutChoferToken`)
- WHEN a pre-change guias app decodes it
- THEN validation succeeds and the unknown keys are ignored without error

### Requirement: Missing Value Rendering

When a transport key is absent or empty, the consumer MUST render it using the existing null-value pattern (`-`), consistent with other optional QR fields.

#### Scenario: Absent driver name

- GIVEN a decoded payload without a `chofer` key
- WHEN the guias header screen renders transport data
- THEN the driver name field displays `-`

### Requirement: No Persistence of Transport Fields

Neither app MUST persist `patenteCamion`, `patenteCarro`, `chofer`, or `rutChoferToken` to local storage as new data. No schema migration MUST be introduced in either repo for this change. When a decoded value auto-selects an existing destination field (per `guias-scan-first-header`), that field MUST be saved only through the pre-existing GDE persistence path already used for a manual selection — this is not new persistence of QR-carried data, and no new column or table is introduced to store the origin QR values themselves.

#### Scenario: No local write of raw QR values

- GIVEN a guias session decodes an origin QR with transport data
- WHEN the header screen displays or auto-selects the values
- THEN no local database write occurs for the origin QR values themselves, and no new table or column exists to store them

#### Scenario: Auto-selected destination field reuses existing save path

- GIVEN the truck plate auto-selects from a catalog match
- WHEN the dispatcher submits the guía
- THEN the truck plate is persisted only through the existing GDE destination-field save path, identical to a manually selected plate

### Requirement: Real Random Cryptographic Keys

The producer and consumer MUST use real, randomly generated 256-bit keys for QR encryption, envelope signing, and RUT-token derivation. The placeholder development key constants currently in `QrTrazabilidadService.js` (the `00112233...` / `ffeeddcc...` values marked "Claves de desarrollo") MUST NOT ship in any build.

#### Scenario: No placeholder key in a shipped build

- GIVEN a production or test build of `movil_comaco` or `movil_comaco_gde`
- WHEN the QR cryptographic keys are loaded
- THEN neither key equals the placeholder `00112233...` / `ffeeddcc...` development constants

### Requirement: Keys Are Server-Provisioned and Rotatable Per Empresa

The QR cryptographic keys MUST be retrieved from server-side configuration (the `PARAMETRO_GENERAL` convention, the same mechanism used for the scan-first fallback flag), scoped per empresa, rather than embedded as constants in the APK. A key MUST be rotatable server-side without requiring an app deployment. Both `movil_comaco` and `movil_comaco_gde` MUST resolve the identical key set for a given empresa so encryption, decryption, and token derivation remain consistent across apps.

#### Scenario: Keys sourced from server configuration

- GIVEN a device needs the QR cryptographic keys for a given empresa
- WHEN it generates or validates a QR
- THEN it retrieves the keys from server-side configuration scoped to that empresa, not from a hardcoded app constant

#### Scenario: Key rotation without app deploy

- GIVEN a key is rotated server-side for an empresa
- WHEN a device performs a subsequent QR operation for that empresa
- THEN it uses the updated key without requiring an app update

#### Scenario: Cross-app key consistency

- GIVEN the same empresa
- WHEN `movil_comaco` encrypts a QR and `movil_comaco_gde` decrypts it, or either derives the RUT token
- THEN both apps resolve the identical key values for that empresa
